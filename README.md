# KBO 시즌 기록 기반 가상야구 · 승부 예측 앱

2026 KBO 정규시즌의 팀·선수 기록으로 두 팀의 가상 경기를 진행하고, 사용자가 승리 팀을 예측해 점수를 쌓는 **Flutter 기반 Android 앱**을 만드는 프로젝트입니다. 경기 계산은 화면과 분리된 **Dart 경기 엔진**으로 구현하며, 최종 산출물은 Android APK, 소스 코드, 시연 자료입니다.

실제 경기의 미래 결과를 맞히는 서비스가 아니라, 실제 시즌 성적을 입력으로 사용하는 가상야구 게임입니다. 현재 **1주 차 데이터 준비·명세·화면 설계, 2주 차 Dart 경기 엔진, 3주 차 Flutter 화면과 엔진 연결, 4주 차 기록 저장·중단 경기 복구, 5주 차 반복 시뮬레이션·확률 보정을 완료**했습니다. Python 데이터 준비 도구, 수집·가공 데이터, 최종 시즌 JSON, 화면 구성안, 독립 실행 가능한 Dart 경기 엔진·CLI 예제와 팀 선택부터 경기 결과까지 진행되는 Flutter 앱(`app/`)이 있습니다. 개인 기록과 진행 중인 경기는 기기에 저장되어 앱을 다시 켜도 복원됩니다. 5주 차에는 20,000경기를 반복 실행해 실제 2026 리그와 비교하고, 아웃 때 주자 진루를 더한 엔진 2.1.0으로 보정했습니다. 다음 단계는 6주 차 Android 기기 검증·APK 빌드·제출 자료 준비입니다.

> 진행 현황 기준: 2026-11-25, 현재 저장된 코드와 JSON 보고서 기준. 아래 주차별 계획은 기존 6주 계획을 따릅니다. 실제 착수일과 주차별 날짜는 별도로 지정하지 않았습니다.

### 사용자 이용 흐름

1. 홈에서 시즌 데이터 준비 상태와 개인 기록을 확인합니다.
2. KBO 10개 팀 중 홈팀과 원정팀을 선택합니다. 같은 팀끼리 대결할 수 없습니다.
3. 팀 전력, 선발투수, 주전 선수와 자동 타순을 비교합니다.
4. 승리할 팀을 선택하고 예측을 확정합니다.
5. 실제 시즌 기록에서 계산한 확률로 가상 경기를 타석 단위로 진행합니다.
6. 최종 점수와 예측 적중 여부를 확인하고 점수를 받습니다.
7. 개인 기록을 저장하고, 앱을 다시 실행하면 기록과 중단된 경기를 복원합니다.

### 첫 버전 범위와 경기 규칙

한 시즌 고정·개인 플레이를 기준으로 전체 선수 기록을 데이터 계층에서 다루고, 경기에는 팀별 자동 선정 타자 9명과 선발투수를 사용합니다. 경기 중 예측한 팀의 투수 교체와 대타는 지원합니다. 경기 전 타순 편집, 수비 교체, 자동 불펜 운용과 전체 가상 시즌은 확장 기능입니다. 로그인, 온라인 랭킹, 실제 금전 거래는 첫 버전에 포함하지 않습니다.

타석 결과는 **삼진, 볼넷, 몸에 맞는 공, 단타, 2루타, 3루타, 홈런, 기타 아웃의 8종**입니다. 타율을 그대로 안타 확률로 사용하지 않고 타석 기준 사건 비율을 사용합니다. 타자 기록은 타석 수, 투수 허용 기록은 상대 타자 수에 따라 리그 평균과 혼합해 소표본을 보정한 후 결합합니다. 확률은 모두 0 이상이고 합이 1이 되도록 정규화합니다. 투수의 피장타 구분 등 세부 항목이 부족하면 리그 평균 비율을 사용하고 보정 근거를 남깁니다. 팀 지표는 전력 비교와 누락 보완에 우선 사용해 선수 능력과 전력을 중복 반영하지 않습니다.

| 타석 결과 | 주자 이동 규칙 (엔진 2.1.0) |
| --- | --- |
| 삼진 | 아웃 1개 증가, 주자는 현재 베이스 유지 |
| 기타 아웃 | 아웃 1개 증가. 0·1아웃에 1루 주자가 있으면 18% 확률로 병살(아웃 2개). 병살이 아니면 3루 주자가 52% 확률로 득점(희생플라이·땅볼 타점)하고, 2루 주자는 3루가 비면 35%, 1루 주자는 2루가 비면 20% 확률로 진루(진루타) |
| 볼넷·몸에 맞는 공 | 타자는 1루, 밀어내기가 필요한 주자만 이동 |
| 단타 | 3루 주자 득점, 2루 주자 60% 득점·나머지 3루, 1루 주자는 3루가 비면 28% 3루·나머지 2루 |
| 2루타 | 2·3루 주자 득점, 1루 주자 42% 득점·나머지 3루 |
| 3루타 | 기존 주자 전원 득점, 타자는 3루 |
| 홈런 | 기존 주자와 타자 모두 득점 |

안타 때 추가 진루율은 프로야구 장기 평균 근사치이고, 병살·득점 아웃 확률은 2026 시즌 시뮬레이션의 병살타/타석과 희생플라이/타석이 실제 리그 값(1.84%, 0.77%)과 맞도록 보정했습니다. 아웃 때 진루율은 5주 차 반복 시뮬레이션에서 득점 부족을 줄이려고 더한 근사치입니다(아래 5주 차 참고). 3아웃이 되는 플레이에서는 득점을 인정하지 않습니다. 도루·실책·폭투·희생번트의 주자 진루는 아직 생략합니다.

- 3아웃마다 공수를 교대하고, 타순은 다음 이닝에도 이어집니다.
- 9회초 종료 후 홈팀이 앞서면 9회말을 생략합니다. 9회말 이후 홈팀이 앞서는 득점이 나오면 끝내기로 종료하고, 끝내기 홈런은 타자와 모든 주자의 득점을 반영합니다.
- 9회 종료 시 동점이면 **최대 11회까지 진행**하고, 11회 종료 후에도 동점이면 무승부로 처리합니다. 2025시즌부터 바뀐 KBO 정규시즌 연장 규정(12회→11회)을 따릅니다.
- 교체하지 않으면 선발투수의 성적을 경기 전체에 적용합니다. 투구 수·피로도와 자동 불펜 교체는 확장 기능입니다.
- 경기 전에는 양 팀 선발투수를 바꿀 수 있습니다. 바꾸지 않으면 자동 선정 선발이 나옵니다.
- 사용자는 예측한 팀만 타석 사이에 교체할 수 있습니다. 수비 중이면 투수 교체, 공격 중이면 대타입니다. 빠진 선수는 다시 나올 수 없고, 대타는 그 타순을 이어받습니다. 투수는 선발·구원 모두 최소 한 타자를 상대한 뒤에만 바꿀 수 있습니다(야구 규칙 5.10).
- 예측 적중 시 100점을 한 번만 지급합니다. 무승부는 0점이며 적중률 분모에서 제외하고 연속 적중은 유지합니다.

### 데이터 연동·저장 설계와 남은 작업

목표 구조는 `외부 API → 변환·검증 → 시즌 JSON 캐시 → Dart 경기 엔진 → Flutter 화면 → 개인 기록 저장`입니다. UI·데이터 조회·경기 계산을 분리하고 외부 DB 없이 구성합니다. 앱은 기본 OCI HTTPS 주소, 검증된 기기 캐시, 앱에 포함된 시즌 JSON 순으로 데이터를 준비하고 엔진 입력 계약·시즌·팀 수 검사를 통과해야 경기를 시작합니다. 원격 실패 시 대체 데이터와 재시도를 안내하며, 모든 입력에 실패하면 원인과 다시 불러오기를 보여줍니다. `KBO_DATA_URL`로 제공처를 바꿀 수 있고 빈 값으로 지정하면 캐시·포함된 데이터로 실행합니다. 실제 OCI 연결·데이터 일치·경기 종료·오프라인 캐시 복원 검증을 통과했습니다.

현재 시즌 JSON 캐시는 `SharedPreferencesAsync`에 저장합니다. 개인 기록과 경기 내역을 기기 내 JSON 파일로 보관하는 기능은 4주 차 계획입니다. 해당 저장 파일에는 데이터 버전을 포함하고 **임시 파일 작성 후 교체**하여 저장 중단에 대비할 예정입니다. 네트워크 오류 시 재시도하거나 기존 시즌 캐시를 사용하는 기능은 구현했습니다. 앱 삭제 시 기기 데이터가 사라질 수 있음을 안내할 예정입니다.

시즌 데이터의 HTTPS 제공은 OCI Object Storage로 구현했습니다. 앱은 공개 시즌 JSON만 읽으며 수집용 API 키나 OCI 인증 정보를 포함하지 않습니다. 데이터 수집 도구는 개발 환경에서 별도로 실행합니다. 제공처의 데이터 이용·재배포 조건과 최종 출처 표기 확인, Android APK 배포 검증은 남아 있습니다.

이적 선수의 공급처 팀별 관측 구간은 원본·합산에 보존합니다. 공식 시즌 합계는 팀별 구간에 임의 배분하지 않고, 앱에서는 공식 시즌 표에 단일 팀으로 분류된 선수만 그 팀에 편입합니다. 소속이 없거나 복수·미지정이면 전체 선수 데이터에는 남기고 자동 편성에서 제외합니다. 같은 선수의 여러 팀 중복 편입은 차단합니다. 이 기준은 시즌 JSON 생성기에 적용했고, 시즌 전체 합계·공식 팀 분류라는 안내 문구도 JSON에 포함했습니다. 앱 전력 비교 화면 하단에도 시즌 전체 합계·공식 팀 분류 기준을 안내합니다.

- 경기 ID, 엔진·데이터 버전, 대진·선발, seed·난수 상태, 이닝·공수·주자·아웃·점수·타순을 관리합니다. 타석 로그에는 타자·투수, 사건 확률·추첨값, 진루 추첨과 득점, 전후 상태가 남습니다.

- 같은 데이터·엔진 버전, 대진·선발·seed와 같은 시점의 교체를 사용하면 같은 경기를 재현합니다. 전체 JSON 비교에는 경기 ID도 같아야 합니다. v1.x, v2.0.0, v2.1.0 로그는 서로 다른 재현 기준입니다.

초기 seed 42 예제는 KT 9:2 삼성, 79타석입니다. v2.0.0 저장 예제는 원정 7:5 홈, 9회·85타석이고, 현재 v2.1.0 예제(같은 대진·seed 42)는 KT 5:4 삼성, 9회·75타석입니다. 예제의 엔진 버전·대진도 함께 확인해야 하며 실제 경기 결과를 뜻하지 않습니다. 엔진 실행·연결 API는 [엔진 사용 안내](dart_engine/README.md)를 참고하고, 현재 엔진 버전과 회귀 검증 기준은 `GameEngine.version` 및 v2.1.0 예제·5주 차 보고서를 사용합니다.

#### 예측·채점과 교체

예측한 팀은 경기 생성 시 확정합니다. 예측 적중은 +100점, 빗나감·무승부는 0점입니다. 무승부는 적중률 분모에서 제외하고 현재 연속 적중을 유지합니다. 빗나가면 현재 연속 적중은 0으로 초기화됩니다. `RecordBook`은 이미 채점한 경기 ID를 검사해 앱 실행 중 동일 경기의 중복 지급을 막습니다. 승패 결정 경기가 없으면 적중률은 `—`로 표시합니다.

경기 화면은 예측한 팀이 공격 중이면 대타, 수비 중이면 투수 교체를 제공합니다. ‘다음 수비까지’ 진행은 내 팀의 수비 시작에서 멈춰 교체를 판단할 수 있게 합니다. 투수 최소 1타자·재출전 금지는 엔진이 검사합니다. 3주 차 당시에는 경기 중 나가려 하면 저장되지 않는다는 확인을 표시했고 기록은 메모리에만 있었습니다. 4주 차부터는 자동 저장되므로 확인 없이 나가고 홈에서 이어합니다.

#### 시즌 JSON 로딩·검증·캐시

```text
Python 수집·공식 대조·라인업 생성
  → 검증된 시즌 JSON
    ├─ OCI 공개 HTTPS 파일
    └─ Flutter 번들 assets/data/season_dataset.json

앱 시작 → HTTPS 요청(10초 제한) → 계약·2026 시즌·10개 팀 검사
            ├─ 성공: 검증된 데이터 사용·기기 캐시 저장
            └─ 실패: 검증된 기기 캐시 → 번들 JSON → 모두 실패하면 오류·재시도

데이터 준비 완료 → 팀 선택·예측 → Dart 엔진 → 경기 결과·실행 중 채점
```

- `DataController`는 `loading / ready / failed` 상태를 관리하며 데이터 준비 전 경기 생성을 막습니다. 겹친 로딩 요청은 진행 중인 하나의 작업으로 합칩니다.
- 응답을 UTF-8로 읽고 `SeasonDataset` 계약을 검사한 다음 캐시를 교체합니다. HTTP 오류·손상 JSON·다른 시즌·규칙 불일치는 정상 캐시를 덮어쓰지 않습니다.
- `PreferencesSeasonCache`는 `SharedPreferencesAsync`를 사용합니다. 캐시 키는 시즌·규칙·원격 주소별로 구분합니다. 캐시 손상이나 저장소 오류가 있어도 번들로 실행할 수 있습니다.
- 대체 데이터로 시작하면 홈에 사용 중인 기록과 재시도를 안내합니다. 모든 입력이 실패하면 오류와 다시 불러오기를 제공합니다. 원격 주소를 빈 값으로 설정하면 캐시·번들로 실행합니다.
- 선수 데이터는 시즌 전체 합계이며 공식 시즌 표의 팀 분류를 사용한다는 설명을 전력 비교 하단에 표시합니다.
- **시즌 캐시 복원은 구현 완료이며 개인 기록·진행 중 경기 복구와 별개입니다.**

#### OCI 원격 데이터 제공

기본 주소는 [OCI 시즌 JSON](https://objectstorage.ap-osaka-1.oraclecloud.com/n/axeqzwyoa6h9/b/kbo-season-data/o/season_dataset.json)이며 `app/lib/data/remote_config.dart`에 정의했습니다. 빌드 시 `KBO_DATA_URL`로 변경할 수 있습니다. 개발 도구에서 시즌 JSON을 만들어 업로드하고 앱은 이 파일만 내려받습니다.

저장된 [실제 연결 보고서](outputs/remote_connection_report.json) 기준 gzip 객체 하나는 114,333바이트, 압축 해제 JSON은 950,762바이트입니다. HTTPS 200·UTF-8·gzip·CORS 응답, 번들과 내려받은 데이터의 일치, 내려받은 데이터로 경기 종료, 통신 실패 시 새 컨트롤러의 캐시 복원을 확인했습니다. 버킷은 객체 다운로드만 공개하고 목록 조회·쓰기는 인증을 요구하며, VM·DB·상시 실행 프로세스를 추가하지 않았습니다. 최초 배치 도구는 `tools/deploy_oci_dataset.py`입니다.

이 결과는 2026-11-19에 저장한 검증 기록이며 현재 외부 서비스의 가용성을 보장하는 표시는 아닙니다. Android 실기기의 통신·플랫폼 저장소 확인과 최종 이용 조건 검토는 남아 있습니다.

- **반복 실행용 seed 편향:** 연속된 작은 seed는 Park–Miller 첫 추첨값이 0에 가까워 모든 경기가 삼진으로 시작했습니다. Park–Miller 수열에서 뽑은 seed는 경기들을 같은 수열의 복사본으로 만들었고, 대진마다 같은 seed 목록을 쓰면 표본이 줄었습니다. 반복 도구는 이제 `dart:math` Random으로 경기마다 다른 seed를 뽑습니다. 앱이 seed를 고르는 방식과 같습니다. 앱은 원래 경기마다 무작위 seed를 써서 영향이 없었습니다.

- **보정(사용자 결정, 2026-11-25):** 새 사건을 만들어 실제 득점에 억지로 맞추지 않고, 빠져 있던 아웃 때 진루만 현실적인 근사치로 더했습니다. 0·1아웃 기타 아웃에서 2루 주자 35%, 1루 주자 20% 확률로 빈 베이스에 진루하고, 문자중계에는 '진루타'로 표시합니다. 남은 득점 차이와 무승부 비율, 홈 이점 미반영은 한계로 기록합니다.
- **호환성:** 시즌 데이터는 바뀌지 않아 OCI 파일을 다시 올릴 필요가 없습니다. 2.0.0에서 저장된 중단 경기는 이어할 수 없고 홈에서 버리기만 제공합니다(기존 동작). 개인 기록은 그대로 유지됩니다.

## 4. 데이터 모델과 저장 구현 상태

시즌 데이터·팀·선수·라인업의 JSON 계약은 [시즌 데이터 계약](docs/season_dataset_contract.md)에 확정했습니다. 경기 상태·타석 로그와 엔진 입력 모델은 `dart_engine/lib/`에 구현했습니다. 아래는 개념 모델입니다. 경기 진행은 `GameState`·`GameEngine`, 완료 경기의 예측 결과는 `GameRecord`, 개인 기록·채점은 `RecordBook`에 구현했습니다. `SimulationGame`·`Prediction`·`PersonalRecord`는 설계상 명칭이며 동일 이름의 저장 모델이 구현됐다는 뜻은 아닙니다. 개인 기록은 `RecordBook`(`kbo_records` v1), 중단 경기는 `SavedGameStore`(`kbo_saved_game` v1)와 엔진 체크포인트로 저장·복구합니다.

| 모델 | 주요 내용 |
| --- | --- |
| `SeasonDataset` | 시즌 ID·연도, 데이터 버전·수집 시각, 검증 상태 |
| `Team` | 팀 ID·이름·약어, 시즌 ID |
| `PlayerSeasonStats` | 공식 선수 ID, 소속 분류, 타격·투구·수비·주루 성적, 누락 정보 |
| `Lineup` | 팀 ID, 주전 9명·포지션·타순, 선발투수, 선정 기준 버전 |
| `SimulationGame` | 가상 경기 ID, 홈·원정, seed·난수 진행 상태, 엔진 버전, 이닝·공수·아웃·주자·점수·타순, 진행 상태·로그 |
| `Prediction` | 경기 ID, 예측 승리 팀, 확정 시각, 채점 여부·지급 점수 |
| `PersonalRecord` | 누적 점수, 예측·승패 결정·적중 횟수, 현재·최다 연속 적중, 최근 경기 |

적중률은 `적중 수 / 승패 결정 경기 수`로 계산하며 분모가 0이면 `—`로 표시합니다. 실제 경기 ID와 가상 경기 ID는 별도로 관리합니다.

## 6. 앱·엔진 실행과 검증 방법

기존 시즌 JSON이 저장되어 있으므로 앱 시연을 위해 데이터를 다시 수집하거나 API 키를 준비할 필요는 없습니다. 앱의 SDK 제약은 Dart `^3.13.7`이며, 기존 실행 기록은 Flutter 3.47.9·Dart 3.13.7 기준입니다. Android 실행에는 Android SDK와 연결된 기기 또는 에뮬레이터가 필요합니다.

### Flutter 앱 실행

프로젝트 루트에서 다음 명령을 실행합니다.

```powershell
cd app
flutter pub get
flutter run
```

웹에서 화면을 확인하려면 `flutter run -d chrome`을 사용합니다. 기본 실행은 OCI HTTPS 파일 다운로드를 시도합니다. 원격 요청을 끄고 캐시·번들로 확인하려면 다음과 같이 실행합니다.

```powershell
flutter run -d chrome --dart-define=KBO_DATA_URL=
```

시연은 홈 데이터 준비 확인 → 원정·홈 선택 → 전력·선발 확인 → 승리 팀 선택·확정 → 다음 타석 또는 다음 수비까지 진행 → 필요시 투수 교체·대타 → 경기 종료·결과 확인 → 홈 점수판·개인 기록 확인 순서로 진행합니다. 개인 기록과 진행 중 경기는 기기에 저장되어 앱을 다시 켜도 이어집니다.

### 독립 Dart 엔진 실행

별도 터미널에서 프로젝트 루트를 기준으로 실행합니다.

```powershell
cd dart_engine
dart pub get
dart run bin/simulate.dart --list-teams
dart run bin/simulate.dart --seed 42 --game-id readme-demo-42
dart analyze
dart run test/engine_test.dart
dart run bin/batch_simulate.dart --seeds 200 --fixed-seeds 2000
dart run bin/calibrate.dart
```

`batch_simulate.dart`는 고정 대진 2,000경기와 90개 대진 18,000경기를 돌려 실제 리그 값과 비교하고, `calibrate.dart`는 아웃 때 진루율별 득점을 계산합니다. 보고서로 남기려면 각각 `--output ../outputs/파일.json`, 첫 인자로 경로를 줍니다. CLI의 기본 입력은 `../kbo_data/kbo_2026_138278/app/season_dataset.json`입니다. 다른 위치에서 실행하거나 다른 파일을 쓰면 `--dataset PATH`를 지정합니다. 기존 검증 산출물을 덮어쓰지 않고 로그를 저장하려면 CLI에 `--output ../outputs/readme_demo_game.json`을 추가합니다.

### Flutter 검사와 웹 빌드

`app/`에서 실행합니다. 실제 OCI 검사는 네트워크를 사용하며 명시적으로 켠 경우에만 실행합니다.

```powershell
flutter test
flutter test --dart-define=VERIFY_OCI_REMOTE=true
flutter build web
```

Windows 한글 경로에서는 기존 실행 중 `flutter analyze` 분석 서버가 비정상 종료되는 문제가 확인됐습니다. 정적 분석용 영문 연결 경로 생성 방법은 [앱 실행 안내](app/README.md)를 따릅니다. 웹 빌드는 글꼴 누락을 피하기 위해 원래 저장소 경로에서 실행합니다. README에 링크한 검증 보고서는 보관 기록이며, 위 명령을 실행한다고 모든 보고서가 자동 갱신되는 것은 아닙니다.

### 시즌 데이터를 갱신한 경우

프로젝트 루트에서 저장된 공식 수정본으로 라인업·최종 입력을 생성하고 Flutter 번들에도 복사합니다.

```powershell
python -m tools.build_lineups
python -m tools.prepare_season_dataset
Copy-Item -LiteralPath kbo_data/kbo_2026_138278/app/season_dataset.json -Destination app/assets/data/season_dataset.json
```

생성기의 검증 성공을 확인한 뒤 복사합니다. 기본 실행은 원격 데이터를 우선하므로 원격 객체도 같은 검증 데이터로 갱신해야 합니다. `tools/deploy_oci_dataset.py`는 최초 배치 도구로, 이미 있는 버킷에서는 중단하므로 기존 객체 갱신 명령으로 사용할 수 없습니다.

## 7. 데이터 도구 실행 방법

아래 명령은 프로젝트 루트(`kbo/`)에서 실행합니다. 데이터 도구는 `tools/`, 테스트는 `tests/`에 있으며, `python -m tools.도구명` 형식을 권장합니다. `python tools/도구명.py`로 직접 실행할 수도 있습니다. 기본 데이터 경로는 실행 위치와 관계없이 프로젝트 루트의 `kbo_data/`를 가리킵니다. 직접 지정한 `--input`·`--output` 상대 경로는 현재 작업 폴더 기준입니다.

### 최종 앱 입력 생성·검증

```powershell
python -m tools.prepare_season_dataset
```

네트워크·API 키 없이 저장된 공식 수정본과 라인업을 읽어 `kbo_data/kbo_2026_138278/app/season_dataset.json`과 `dataset_validation_report.json`을 생성합니다. 다른 폴더는 `--input`으로 지정합니다. 선수 수정본을 갱신했다면 `python -m tools.build_lineups`를 먼저 실행하세요. 오래된 라인업 해시, 부정합 통계, 선정 선수 필수 기록 누락·중복·소속 불일치가 있으면 생성을 중단합니다. 성공 종료 코드 0은 데이터 입력 검증 완료이며 Dart·Flutter 구현 완료를 뜻하지 않습니다.

### KBO 정규시즌 경기 수집

Python 3.10 이상, 외부 패키지 없이 실행합니다.

```powershell
python -m tools.fetch_kbo --season 2026
```

`SPORTRADAR_API_KEY` 환경 변수가 없으면 키를 비공개 입력으로 받습니다.
키를 소스 코드나 JSON에 저장하지 않습니다.

기본 동작은 API가 제공하는 해당 시즌의 **종료된 정규시즌 경기 전체** 수집입니다.
포스트시즌, 취소 경기, 미종료 경기는 제외합니다. 시즌 진행 중에는 실행 시점에
종료된 경기만 포함합니다. 팀 목록과 경기 목록은 실행할 때마다 새로 조회합니다.

## 나누어 수집하거나 이어받기

```powershell
python -m tools.fetch_kbo --season 2026 --max-games 50
```

이번 실행에서 경기 상세를 최대 50건 조회합니다. 같은 명령을 다시 실행하면
정상 저장된 경기는 건너뛰고 남은 경기를 받습니다. 기본값 `--max-games 0`은
상세 조회 건수를 제한하지 않습니다. 목록 조회와 HTTP 재시도는 이 건수에 포함하지 않습니다.
Ctrl+C로 중단한 뒤 같은 명령으로 이어받을 수도 있습니다.

원본의 경기 ID, 정규시즌 종료 상태, 비어 있지 않은 선수 기록을 확인한 뒤
완료로 처리합니다. 원본이 정상이면 가공 파일이 없거나 손상되어도 재생성합니다.
실패, 통계 미제공, 원본 손상 경기는 다음 실행에서 다시 조회합니다.
`complete`는 선수 기록이 있는 응답을 저장했다는 의미이며 모든 통계 필드의
제공이나 정확성을 보증하지는 않습니다. 미제공 항목을 0으로 채우지 않습니다.

## 제공처의 수정 기록 다시 받기

```powershell
python -m tools.fetch_kbo --season 2026 --refresh
```

이 옵션은 이미 저장된 경기 상세도 다시 조회합니다. 전체 갱신에는
`--max-games`를 함께 지정하지 않는 편이 좋습니다. 갱신 옵션과 건수 제한을
함께 반복하면 매번 목록 앞쪽 경기부터 다시 조회합니다.

## 저장 파일과 수집 현황

`kbo_data/kbo_2026_138278/` 아래에 저장합니다. 폴더의 시즌 ID는 API 응답에 따릅니다.

- `teams.json`: 시즌 참가 팀.
- `raw/summaries_*.json`: 경기 목록 페이지 원본.
- `sr_sport_event_*/game_raw.json`: 각 경기 상세 원본.
- `sr_sport_event_*/player_stats.json`: 해당 경기의 선수 기록. 시즌 누적 기록이 아닙니다.
- `collection_status.json`: 현재 조회한 목록 기준 대상 수, 완료·대기·실패·통계 미제공 건수와 경기별 상태.

`game_list_complete=true`이면 전체 목록 조회가 끝났고, `all_complete=true`이면
대상 경기가 한 건 이상이며 모두 선수 기록을 저장했습니다. 경기마다 현황을 저장합니다.
401·403·429 오류는 추가 호출을 중단합니다. 429는 제한된 재시도 후 중단하며,
한도가 회복된 뒤 다시 실행합니다. 그 외 경기 요청 오류는 기록하고 다음 경기로 진행합니다.
파일 쓰기 실패 시에는 중단합니다. 마지막 현황 저장 직후 강제 종료하면
다음 실행에서 실제 저장 파일을 다시 검사해 현황을 복구합니다.

종료 코드: `0` 전체 완료, `1` 실행 오류, `2` 건수 제한·개별 실패·통계 미제공 등으로 미완료.
실제 총 경기 수는 고정하지 않고 전체 목록에서 경기 ID 중복을 제거해 계산합니다.
이 수집기는 라인업 추가 조회는 수행하지 않습니다. 시즌 합산은 아래 별도 명령으로 실행합니다.

## 팀·선수 시즌 합산과 누락 표시

```powershell
python -m tools.aggregate_kbo
```

다른 시즌 폴더는 `--input kbo_data/해당_시즌_폴더`로 지정합니다.
네트워크 호출 없이 원본을 읽어 `aggregated/` 폴더에 다음 파일을 만듭니다.
수집을 다시 한 경우 이 명령도 다시 실행하면 갱신됩니다. 원본과 수집 현황은 변경하지 않습니다.

- `team_season_stats.json`: 팀별 경기 수·승패·무승부·득실점, 원본 팀 통계 합산.
- `player_season_stats.json`: 선수 ID + 팀 ID 기준 통계 합산. 이적 선수의 팀별 기록 보존.
- `aggregation_report.json`: 누락 경기, 영향받는 팀, 원본 데이터 품질 문제 상세.

팀 승패·득실점은 전체 경기 최종 점수 기준입니다. 팀 상세 통계와 선수 기록은
제공된 항목만 더하고, 누락·유효하지 않은 값의 건수와 대상 경기 ID를 표시합니다.
현재 롯데–KIA 1경기의 선수 통계가 없어 두 팀 선수에
`possibly_incomplete_due_to_team_missing_games=true`를 붙입니다. 실제 해당 경기
출전 여부는 알 수 없으므로 `participation_in_missing_games=unknown`으로 표시합니다.
누락 경기에만 등장하고 다른 기록이 전혀 없는 선수는 명단에 포함할 수 없습니다.

`observed_statistics`는 관측된 유효 값의 합계입니다. 해당 필드의 유효 값이
하나도 없으면 `null`, 일부만 없으면 관측 합계와 누락 건수를 함께 기록합니다.
`coverage`의 완전성은 제공된 항목과 수집 범위에 관한 것이며 공식 기록의 정확성을 보증하지 않습니다.
`games_with_records`는 기록이 있는 경기 수이며 공식 출장 경기 수가 아닙니다.

원본 역할 표기가 일관되지 않아 타자·투수 역할이 바뀌어도 같은 선수·팀으로
합산하고 `source_role_record_counts`에 원래 역할별 건수를 보존합니다.
타자로 표시됐는데 투구 이닝이 양수인 경우와 팀 통계/선수 합계 불일치는
보고서에 남기며 임의로 수정하지 않습니다. 원본 `strikeouts`는 그대로 보존하되
그 의미를 투수 탈삼진으로 단정하지 않습니다.

투구 이닝은 야구의 `n.1`, `n.2` 표기를 아웃 수로 바꿔 합산합니다.
예: `0.2 + 0.1 = 1.0`. 출력은 `outs_pitched` 정수와 `innings_pitched` 문자열입니다.
원본 소수 이닝이 이 표기 규칙을 따른다는 전제는 메타데이터에도 명시합니다.
타율과 평균자책점은 관측 기록으로 계산하며 해당 필드에 무효·누락 값이 있으면
`null`입니다. 누락 경기의 영향은 별도 `coverage`를 확인해야 합니다.
출루율·장타율·OPS는 필요한 항목이 없어 계산하지 않습니다.
안타/타수·자책점/이닝 등의 원본 불일치는 그대로 반영될 수 있으므로 공식 기록으로 사용하지 마세요.

## 포지션·시즌 전체 라인업 수집

```powershell
python -m tools.fetch_kbo_lineups
```

기존 `kbo_data/kbo_2026_138278`를 기준으로 동작합니다. 다른 시즌은
`--input kbo_data/해당_시즌_폴더`로 지정합니다. API 키는 기존 수집기와 같이
환경 변수 `SPORTRADAR_API_KEY` 또는 화면에 표시되지 않는 입력으로 받습니다.

1. 기존 종료 정규시즌 경기 목록과 원본의 시즌·경기 ID·시간·홈/원정을 검증합니다.
2. 시즌 라인업을 페이지당 100경기씩 받아 기존 경기 ID와 대조합니다.
3. 누락·불완전·중복 충돌이 있는 경기는 경기별 라인업 API로 보완합니다.
4. 팀 프로필의 선수 포지션을 받고, 기존 선수 중 포지션이 여전히 없는 선수는 개인 프로필로 추가 조회합니다.
5. 원본과 가공 결과, 검증 현황을 `supplemental/` 아래에 저장합니다.

동일 명령을 다시 실행하면 검증된 저장 응답을 재사용하고 미완료 항목을 다시 조회합니다.
저장된 시즌 페이지도 재사용하므로 제공처 수정 데이터를 받으려면 `--refresh`를 지정합니다.
경기별 보완을 나누려면 `--max-games 50`을 지정할 수 있습니다. 이는 시즌 페이지와
프로필 호출 수를 제한하지 않습니다. 401·403·429는 중단하고 현재 현황을 저장합니다.

- `supplemental/season_lineups.json`: 기존 경기 ID에 연결한 경기별 라인업.
- `supplemental/player_positions.json`: 기존 선수 ID에 연결한 포지션과 출처별 관측 기록.
- `supplemental/collection_status.json`: 전체 대상/검증 통과 수, 포지션 미확보 선수 ID,
  누락·불일치 경기 ID와 요청 오류. 경기별 자세한 오류는 `season_lineups.json`의 `errors` 확인.
- `supplemental/raw/`: 시즌 페이지, 경기별 라인업, 팀·개인 프로필 원본.

각 경기의 `valid=true`는 경기·팀 ID와 홈/원정·시간이 일치하고, 선발 타자 9명의
타순이 정확히 1~9이며, 선발투수가 한 명으로 식별되고 선발 포지션 코드가 제공됐다는 뜻입니다.
교체 선수는 같은 타순을 물려받을 수 있으므로 타순 유무로 선발을 추측하지 않습니다.
`starter=true`인 선수만 선발로 사용합니다. 중복 선수 ID와 상대 팀 통계에 연결되는 선수도 차단합니다.
기존 선수 통계가 없는 경기/선수는 별도 경고이며 선발 라인업만으로 통계 누락을 메우지 않습니다.

포지션은 제공처의 분류이며 `IF`/`OF` 같은 넓은 범위가 있을 수 있습니다.
라인업의 `type`도 그 경기의 정확한 수비 위치를 보장하지 않습니다. 프로필은 현재 시점의
스냅샷이므로 과거 소속이나 경기별 포지션을 덮어쓰지 않습니다. 여러 포지션이 관측되면
하나로 임의 확정하지 않고 모든 코드와 출처를 보존합니다. 이름은 연결 키로 사용하지 않습니다.

`all_complete=true`는 기존 대상 경기 모두가 구조 검증을 통과하고, 팀 프로필을 받았으며,
기존 선수 ID 모두에 포지션 근거가 있다는 뜻입니다. 공식 기록과 독립 대조를 했다는 뜻은 아닙니다.
시즌 페이지 조회에 실패해도 모든 대상 경기를 개별 조회로 보완했다면 완료로 처리합니다.
종료 코드 `0`: 완료, `1`: 실행 중단/오류, `2`: 누락 또는 검증 미완료.

공식 문서:
[시즌 라인업](https://developer.sportradar.com/baseball/reference/global-baseball-season-lineups),
[팀 프로필](https://developer.sportradar.com/baseball/reference/global-baseball-competitor-profile),
[선발·타순 사용 안내](https://developer.sportradar.com/baseball/docs/global-baseball-ig-retrieving-team-and-player-details).

## KBO 공식 기록 대조·수정본

`python -m tools.reconcile_kbo`는 KBO 공식 사이트에서 해당 연도와 정규시즌을 명시적으로
선택해 팀·선수 전체 기록을 받고, 720경기의 공식 경기 목록과 박스스코어를 대조합니다.
이미 받은 경기별 공식 JSON은 재사용합니다. `--games-only`는 시즌 표를 재수집하지 않고
경기별 대조만 수행합니다. `--offline`은 저장된 시즌 표로 시즌 수정본만 재생성합니다.

- `aggregated/corrected_team_season_stats.json`: 공식 기록 기준 팀 시즌 수정본.
- `aggregated/corrected_player_season_stats.json`: KBO 선수 ID 기준 공식 시즌 기록.
  타격·투구·수비·주루 항목을 구분하며 투수 탈삼진과 타격 삼진을 별도로 제공합니다.
- `official/reconciliation_report.json`: 시즌 팀 수정 전후와 선수 연결 후보 차이.
- `official/game_reconciliation_report.json`: 경기별 공식 자료 대조 결과 및 팀 수정 전후.
- `official/games/*.json`: 기존 경기 ID와 연결한 공식 박스스코어 기반 수정본.
- `official/official_tables.json`, `official/raw/`: 공식 원본과 출처·수집 시각·해시.

**기존 Sportradar 원본과 기존 합산 파일은 보존됩니다. 새로 사용하는 시즌 데이터는
`corrected_*` 파일을 기준으로 선택하세요.** 공식 선수 ID와 Sportradar 선수 ID는 다릅니다.
이름·팀으로 찾은 후보는 `official/player_id_candidates.json`에 보관하며 신원 확정으로
간주하지 않습니다. 동명이인·외국인 표기 차이·이적 구간을 이름만으로 강제 병합하지 않습니다.
공식 선수 시즌 기록은 시즌 전체 값이며 기존 팀별 이적 구간에 배분하지 않습니다.
경기별 공식 박스스코어는 선수 이름만 제공하므로 해당 이름을 기존 선수 ID에 임의 연결하지 않습니다.

시즌 수정본에서 제공되는 값과 경기별 수정본에서 제공되는 값의 범위는 다릅니다.
경기별 타격은 타수·안타·타점·득점과 원문 타석 결과, 투구는 이닝·피안타·피홈런·
탈삼진·실점·자책점 등을 제공합니다. 공식 경기 표의 `4사구`는 볼넷과 사구의 합계이므로
`walks_and_hit_batters`로 보존하며 볼넷만의 값으로 바꾸지 않습니다.
시즌 표의 팀 타격 볼넷·삼진은 이번 팀 타격 표에 없어 미검증이며,
기존 선수 ID별 모든 원본 항목의 교정이 끝났다는 의미는 아닙니다.

공식 출처: [KBO 타격 기록](https://www.koreabaseball.com/Record/Player/HitterBasic/Basic1.aspx),
[KBO 투구 기록](https://www.koreabaseball.com/Record/Player/PitcherBasic/Basic1.aspx),
[KBO 게임센터](https://www.koreabaseball.com/Schedule/GameCenter/Main.aspx).

## Sportradar ↔ KBO 선수 ID 연결

```powershell
python -m tools.resolve_player_ids --collect-profiles
```

API 키를 환경 변수 또는 비공개 입력으로 받습니다. 먼저 저장된 공식 경기에서
이름·팀으로 공식 ID가 하나로 구분되고, 서로 다른 3경기 이상의 유효한 타격/투구
수치가 정확히 일치하며, 다른 공급처 ID와 충돌하지 않는 연결을 확인합니다.
보류된 공급처 ID만 프로필을 조회해 생년월일을 공식 프로필과 대조합니다.
공식 시즌 기록에 없는 선수는 KBO 선수 검색 결과의 현역·은퇴·퓨처스 선수 ID도 확인합니다.

생년월일만 같다고 연결하지 않습니다. 이름도 호환되거나, 신장과 경기 기록이 함께
일치해야 하며 후보가 둘 이상이면 계속 보류합니다. 원본 역할이 잘못된 경우를 고려해
역할 문자열만으로 신원을 확정하지 않습니다. 공급처 API 호출 간격을 지키므로 추가 수집은
몇 분 걸릴 수 있습니다. 같은 명령을 다시 실행하면 저장된 프로필을 재사용합니다.
`--max-profiles 50`은 이번 실행의 Sportradar 프로필 요청 수를 제한합니다.

- `official/identity/player_id_crosswalk.json`: 연결된 ID와 방법·증거, 미해결 사유.
- `official/identity/unresolved_player_ids.json`: 추가 확인이 필요한 ID만 모은 파일.
- `aggregated/linked_player_season_stats.json`: 공식 시즌 기록에 확인된 공급처 ID를 추가한 파일.

프로필 수집 없이 저장된 자료만 재검증하려면 `python -m tools.resolve_player_ids`를 실행합니다.
종료 코드 `0`은 전체 연결, `2`는 일부 보류입니다. 기존 후보 파일을 이름만으로 확정 처리하지 않습니다.

## 시즌 성적 기반 선발·주전·타순

```powershell
python -m tools.build_lineups
```

공식 시즌 수정본을 읽어 `aggregated/team_lineups.json`에 10개 팀의 선발투수와
포지션·타순을 포함한 주전 9명을 저장합니다. KBO 선수 ID만 사용하며 공급처 ID 연결은 필요하지 않습니다.

- 선발투수: 선발 20회 이상, 100이닝 이상 중 ERA가 가장 낮은 선수.
  동률이면 WHIP, 투구 아웃 수 순입니다. 이 기준은 자체 선정 규칙입니다.
- 타자: 144타석 이상. 수비수는 해당 자리 선발 10회 이상 또는 수비 30이닝 이상의 경험이 필요합니다.
- 포지션: 수비 8자리와 DH를 모두 채우며 한 선수를 중복 배치하지 않습니다.
  선수별 출루율·장타율에 리그 평균 200타석을 가산해 표본을 보정하고,
  타석 수와 해당 포지션 선발 경험에 소폭 가점을 더한 합계를 최대화합니다.
- 타순: 보정 장타율로 4번, 보정 OPS로 2번, 보정 출루율로 1번,
  보정 OPS로 3번, 보정 장타율로 5번을 선택한 뒤 나머지는 보정 OPS 순으로 배치합니다.
  매번 이미 선택한 선수를 제외합니다.

실제 역사적 라인업이나 득점을 수학적으로 최대화한다고 검증된 타순은 아닙니다.
부상·좌우 상대 성적·현재 등록 명단은 반영하지 않았고, 공식 시즌 표의 팀 분류를 사용합니다.
메타데이터에 원본 해시와 선정 규칙, 선수별 수비 출장 근거·성적을 함께 보존합니다.
